# 2. Назначение и границы проекта

## 2.1. Назначение системы

Разрабатываемая программная система предназначена для автоматизации учета клиентов, абонементов, тренировок и посещений фитнес-центра.

Пользователь системы (сотрудник рецепции) должен иметь возможность:

- добавлять, удалять и редактировать данные клиентов;
- искать клиентов по ФИО и телефону;
- оформлять клиенту абонемент с выбором типа;
- видеть автоматически рассчитанную дату окончания абонемента;
- просматривать список активных и завершенных абонементов;
- отмечать факт посещения клиентом фитнес-центра;
- формировать отчеты по проданным абонементам и посещаемости.

Сотрудник с правами администратора должен иметь возможность:

- добавлять и изменять типы абонементов;
- управлять учетными записями пользователей системы;
- просматривать расширенные финансовые отчеты.

---

## 2.2. Основные объекты предметной области

В системе выделены следующие основные сущности:

- клиент;
- абонемент;
- тип абонемента;
- посещение;
- сотрудник (пользователь);
- роль пользователя.

Примеры типов абонементов:

- Разовое посещение;
- Месячный безлимит;
- Годовой с бассейном.

---

## 2.3. Границы проекта

### В систему входит

1. Ведение базы клиентов.
2. Оформление и учет абонементов.
3. Автоматический расчет срока действия абонемента.
4. Регистрация посещений.
5. Проверка актуальности абонемента при визите.
6. Отчеты по клиентам, абонементам, посещаемости.
7. Авторизация пользователей в системе.
8. Хранение истории операций.

### В систему не входит

В рамках курсового проекта не реализуются:

- реальные банковские платежи;
- интеграция с терминалами оплаты;
- интеграция с турникетами и электронными замками;
- мобильное приложение для клиентов;
- онлайн-расписание и запись через сайт;
- автоматическая отправка SMS и e-mail.

Эти функции могут быть добавлены при дальнейшем развитии проекта.

# 4. Перечень модулей системы

На стороне серверного API выделено четыре основных функциональных модуля.

| Модуль | Ответственность |
|---|---|
| `CustomerModule` | Хранение информации о клиентах |
| `MembershipModule` | Оформление и управление абонементами |
| `VisitModule` | Регистрация посещений и контроль сроков |
| `ReportModule` | Формирование статистических отчетов |

Дополнительно используется точка входа (FastAPI Host), которая принимает HTTP-запросы от WPF-клиента и передает их соответствующим модулям.

---

## 4.1. CustomerModule

Отвечает за работу с профилями клиентов.

Основные функции:

- регистрация клиента;
- получение данных клиента;
- изменение контактных данных;
- поиск по базе.

Пример состояний клиента:

```text
Active
Blocked
```

---

## 4.2. MembershipModule

Отвечает за абонементы.

Основные функции:

- создание абонемента;
- расчет дат начала и окончания;
- отмена абонемента;
- предоставление данных об активности абонемента.

Модуль взаимодействует с:

```text
CustomerModule
```

---

## 4.3. VisitModule

Отвечает за отметки посещений.

Основные функции:

- регистрация нового посещения;
- проверка актуальности абонемента;
- хранение истории визитов.

Пример состояний посещения:

```text
Registered
Cancelled
```

---

## 4.4. ReportModule

Отвечает за формирование сводной информации.

Основные функции:

- агрегация данных о посещаемости;
- расчет проданных абонементов за период.

# 5. Архитектурная схема

Для проекта выбрана клиент-серверная архитектура с модульным бэкендом.

```text
                         ┌──────────────────┐
                         │    WPF-Клиент    │
                         └────────┬─────────┘
                                  │
                                  │ HTTP
                                  ▼
                         ┌──────────────────┐
                         │   FastAPI Host   │
                         │    (REST API)    │
                         └────────┬─────────┘
                                  │
                 ┌────────────────┼─────────────────┐
                 │                │                 │
                 ▼                ▼                 ▼
        ┌────────────────┐ ┌───────────────┐ ┌────────────────┐
        │  VisitModule   │ │CustomerModule │ │  ReportModule  │
        └───────┬────────┘ └───────▲───────┘ └────────────────┘
                │                  │
                │ проверка         │ проверка
                │ абонемента       │ клиента
                ▼                  │
        ┌────────────────┐         │
        │MembershipModule├─────────┘
        └───────┬────────┘
                │
                │
                ▼
        ┌────────────────┐
        │  База данных   │
        └────────────────┘
```

Центральным модулем бизнес-процесса рецепции является `VisitModule`.

При отметке посещения он:

1. получает запрос от WPF-клиента;
2. запрашивает у модуля абонементов актуальность контракта;
3. при успешной проверке создает запись о визите;
4. сохраняет данные в БД.

# 10. Описание API

WPF-клиент взаимодействует с системой через HTTP API.

Предполагаются следующие основные точки входа.

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/api/v1/customers` | Получение списка клиентов |
| `POST` | `/api/v1/customers` | Регистрация клиента |
| `POST` | `/api/v1/memberships` | Оформление абонемента |
| `GET` | `/api/v1/memberships/{id}` | Получение абонемента |
| `POST` | `/api/v1/visits` | Регистрация посещения |
| `GET` | `/api/v1/reports/visits` | Получение отчета |

Контракт API на последующих этапах может быть дополнительно описан средствами OpenAPI (Swagger).

# 11. Протокол взаимодействия № 1  
## Проверка актуальности абонемента

### 11.1. Инициатор и получатель

**Инициатор:**

```text
VisitModule (Сервер)
```

**Получатель:**

```text
MembershipModule (Сервер)
```

---

### 11.2. Назначение

Протокол используется при регистрации визита.

Перед сохранением посещения необходимо убедиться, что выбранный абонемент активен на текущую дату.

---

### 11.3. Механизм вызова

Асинхронный вызов через внутренний интерфейс сервиса.

---

### 11.4. Точка входа

```python
async def check_validity(request: MembershipCheckRequest) -> ValidationResult:
```

---

### 11.5. Формат запроса

```json
{
  "membershipId": "a1b2c3d4-e5f6-7890-1234-56789abcdef0",
  "visitDate": "2026-10-15T18:30:00"
}
```

---

### 11.6. Успешный ответ

```json
{
  "isValid": true,
  "errorCode": null
}
```

---

### 11.7. Ошибки

Возможные ошибки:

| Код | Описание |
|---|---|
| `MEMBERSHIP_NOT_FOUND` | Абонемент не существует |
| `MEMBERSHIP_EXPIRED` | Срок действия абонемента истек |
| `MEMBERSHIP_BLOCKED` | Абонемент заблокирован |

Пример:

```json
{
  "isValid": false,
  "errorCode": "MEMBERSHIP_EXPIRED"
}
```

---

### 11.8. Таймаут

Операция должна завершиться не более чем за:

```text
2 секунды
```

---

### 11.9. Повторная отправка

Автоматический повтор внутренней операции не выполняется.

Причина: состояние абонемента не меняется динамически в рамках миллисекунд.

---

### 11.10. Аутентификация

Дополнительная аутентификация между модулями не выполняется, поскольку они работают внутри одного процесса бэкенда.

Проверка JWT-токена пользователя выполняется на уровне FastAPI.

---

### 11.11. Версия контракта

```text
MembershipValidationContract v1
```

---

### 11.12. Пример обмена

```text
VisitModule
      │
      │ check_validity(...)
      ▼
MembershipModule
      │
      │ Поиск абонемента
      │
      │ Проверка сроков действия
      │
      ▼
ValidationResult
      │
      ▼
VisitModule
```

При успешной проверке `VisitModule` продолжает сохранение визита.

При ошибке `MEMBERSHIP_EXPIRED` визит отклоняется, и клиенту возвращается HTTP 400.

# 15. Тестовая стратегия

Для проекта предусматриваются несколько уровней проверки.

## 15.1. Модульные тесты бэкенда

Проверяют отдельные правила предметной области.

Примеры:

### Тест 1

Абонемент доступен на указанную дату.

**Ожидаемый результат:** валидация выполняется успешно (True).

### Тест 2

Срок абонемента истек вчера.

**Ожидаемый результат:**

```text
MEMBERSHIP_EXPIRED
```

---

## 15.2. Интеграционные тесты

Интеграционные тесты проверяют взаимодействие HTTP-маршрутов и базы данных.

### Сценарий 1. Успешная регистрация визита

Ожидается:
- возвращен HTTP 200;
- в базе появилась запись.

### Сценарий 2. Ошибка при заблокированном клиенте

Ожидается:
- абонемент не создан;
- возвращен HTTP 400.

---

## 15.3. Проверка сборки

После внесения изменений должны выполняться автотесты и сборка WPF-проекта. Критерием успешного результата является отсутствие ошибок.

# 17. Правила коммитов

Один коммит должен содержать одно логически завершенное изменение.

Используются следующие обозначения:

```text
feat: новая функциональность
fix: исправление
docs: документация
test: тесты
```

## ADR-001. Использование клиент-серверной архитектуры

### Статус

Принято.

### Проблема

Система должна безопасно хранить данные централизованно, а интерфейс рецепции должен быть быстрым и работать на ОС Windows.

### Решение

Разделить приложение на WPF (толстый клиент) и FastAPI (сервер).

### Причина

Такое разделение позволяет:

- безопасно управлять доступом к БД на сервере;
- использовать богатые возможности интерфейса WPF;
- в будущем подключить мобильное приложение к тому же API.

---

## ADR-002. Взаимодействие модулей на бэкенде

### Статус

Принято.

### Проблема

Прямое обращение одного модуля к таблицам БД другого модуля создает жесткую связанность.

### Решение

Взаимодействие модулей выполнять через внутренние интерфейсы сервисов.

Например:

```text
VisitModule -> IMembershipValidationService
```

### Последствия

Положительные:

- модули слабее связаны;
- проще писать unit-тесты.

# 23. Оставшиеся риски

На данном этапе выявлены следующие риски.

### Риск 1. Потеря сети клиентом

При разрыве соединения WPF-клиента с сервером приложение может зависнуть.

Необходимо реализовать асинхронные вызовы и глобальную обработку исключений `HttpRequestException`.

### Риск 2. Ошибка сохранения при успешной проверке

Абонемент может быть валиден, но сохранение визита завершится ошибкой БД.

Необходимо корректно возвращать код 500 и транслировать понятное сообщение в WPF.

### Риск 3. Часовые пояса

Рассинхронизация времени на ПК-клиенте и сервере может привести к ошибкам валидации дат.

Необходимо использовать UTC-время для всей бизнес-логики.
